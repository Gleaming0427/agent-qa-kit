# One case per plausible wrong implementation: rule 5 measured, 4 November 2026

Rule 5 of `.claude/agents/qa-writer.md` asked for "at least one case where a plausible wrong implementation shows a different result". Since commit e9f30f4, it asks for a case for each plausible wrong implementation of each rule a criterion combines, and for the evidence to name the one each case rules out ([2026-11-04-eval-1-ac-1.md](2026-11-04-eval-1-ac-1.md) gives the reason). The examples of the rule did not change.

## The plan, written before the results

Committed before QA eval run 41834419007 (run 35: every ticket, 3 trials, the new prompt) finished, so the reading cannot follow the results.

- **The decision** is the release decision of run 35, under the rules at its commit. The reference is D clean, the release baseline, with run 34 for EVAL-17 (the agent of D clean, 3 trials). The comparison pools each side's trials ticket by ticket.
- **A second reading** pools every campaign of D clean's agent as the reference:
  - D clean;
  - its regression check;
  - the split-runner campaign;
  - smoke runs 30 and 32;
  - follow-up run 33;
  - run 34.

  It gives the reference more trials on the tickets that varied (EVAL-1: 15). It informs; it does not decide.
- **What would show that the rule works:** EVAL-1's bug `discount-includes-shipping` detected more often than D clean's agent did (7 of its 15 trials), with AC-1 cases where shipping is paid. With 3 trials, only a large change can be read: 3/3 against 7/15 is a hint, not a proof. The ticket that revealed the problem cannot validate its fix on its own.
- **What would show a cost:**
  - a ticket or a bug worse on the other tickets;
  - more turns, a longer phase 1, or a higher cost per trial;
  - more false positives, since more cases are more chances to assert something the spec does not say.
- **EVAL-17** was written after reading EVAL-1's misses, as a ticket the new rule was not tuned on. The agent of D clean already passed it 3/3, with every bug detected (run 34). It can show a loss, not a gain.
- **Nothing is concluded** from a single campaign where the trials disagree. A ticket that gets worse gets one follow-up, as the release decision asks.

### What the rule changed

- **EVAL-1 passed 3/3, with `discount-includes-shipping` detected 3/3, against 7/15 before.** Each trial wrote two AC-1 cases: one under €50 with paid shipping, one at €53.50. Each evidence names the discount taken on the subtotal plus shipping among the wrong implementations it rules out. For instance, trial 3: "Backpack alone: Discount €4.90, Shipping €4.90, Total €49.00. This rules out a discount taken on subtotal plus shipping, which would give €5.39 off".
- **5 trials had a false positive, against 2 in 48 for the reference.** The failing tests were run again on the reference implementation to read their messages:
  - **4 wrong expected amounts**, in cases with several products or steps:
    - EVAL-17 trial 3 expects a total of €24.40 after a fourth unit, where it is €28.40;
    - EVAL-8 trial 2 expects €15.40 at its second step, where it is €21.40;
    - EVAL-11 trial 3 counts 3 × €6.00 as €12.00, so €50.90 where it is €56.90;
    - EVAL-12 trial 1 adds €29.90, two €6.00 and €4.50 to €44.60 instead of €46.40, so its hint reads €5.40 where it is €3.60.
  - **1 assumption the spec does not make:** EVAL-8 trial 3's browser tests expect two "Checkout" buttons, and the reference has one. Its miss of `bar-hidden-on-phones` follows from it: the test that would catch the bug also fails on the reference, so it detects nothing.
- **Every ticket that got worse got worse through these false positives.** Bug detection did not drop elsewhere.
- **Each trial costs more:** about 10% more per trial, and 9 s more for phase 1 at the median.

## The reading, against the plan

- **The rule does what it was written for.** EVAL-1's shipping bug went from 7 of 15 to 3 of 3, through the case the earlier trials left out. With 3 trials, on the ticket that revealed the problem, that is a strong hint, not a proof.
- **It has the cost the plan expected.** False positives went from 2 to 5 in 48 trials, mostly wrong expected amounts in the cases the rule adds. More cases mean more amounts to work out by hand, and more chances to get one wrong.
- **No clear change in trial success.** The gain in detection is paid in false positives:
  - 94.1% → 90.2% against D clean and run 34;
  - 89.1% → 90.2% against every campaign of D clean's agent.
- **EVAL-17 tells nothing about the gain.** D clean's agent passed it 3/3. Rule 5 passed it 2/3, through one wrong amount.
- **Not released.** The decision is review, and the release baseline stays D clean.
  - The branch now carries the new rule 5, so its next campaigns measure the new agent.
  - Keeping it, reverting it, or changing it again is a decision to take.

## What could come next, not done

- **Run the follow-up of EVAL-12 and EVAL-17** (6 trials) once the credit allows, and validate again with runs 35 and 36.
- **A change aimed at the false positives:** ask the agent to work out each expected amount from the spec's figures and check it before writing it. It would be a change of its own, measured the same way. A wrong amount still fails on the shop as it is, so the RED check of phase 1 cannot catch it; only the reference implementation does.

## Decision: back to the previous rule 5

The branch goes back to the rule 5 of D clean, the release baseline. The writer's prompt is again the one of D clean's agent.

- The new rule was not accepted: the decision is review.
- It trades a gain in detection for as many false positives, with no clear change in trial success, at about 10% more per trial.
- Measuring a corrected version costs campaigns that are not worth their price now.

The rule that was measured, from commit e9f30f4, for a later attempt:

> 5. Choose test data that separates the specified behavior from plausible mistakes. For each criterion, note the rules it combines (what a value is computed on, a threshold, which item an action targets) and the plausible wrong implementations of each rule. Give each wrong implementation a case where it shows a different result: apply the rule while another rule also applies (a fee is charged, a limit is reached), act on an item that is neither the first nor the only one, use values on each side of a threshold. One case seldom rules out every wrong implementation of a criterion: a case where a correct and a wrong implementation show the same result proves nothing about that one. In the evidence, name the wrong implementation each case rules out.

A later attempt should change it together with a check of the expected amounts, and be measured on a smoke run first (QA eval's `max_cost_usd` caps the estimate, 5 dollars by default).
